## J-2026-10-10-E — L'auto-test trouve cinq contrôles muets à sa première exécution

> type : constat · ref : fichier:tests/test_autotest.py

Première exécution de `socle selftest` : cinq défauts injectés passaient
sans bruit — code changé sans sa doc, entrée de journal réécrite, fait
effacé, valeur attendue changée, mémoire en retard. Cause unique : sur une
branche sans commit propre, la base de travail retombait sur `HEAD~1`, qui
n'existait pas, et tous les contrôles comparés à la base se taisaient aux
étages agent et git. Corrigé dans `outils.base_de_travail` : la base est le
point de divergence, même égal à HEAD.

L'auto-test lui-même avait un trou : il tenait un défaut pour attrapé dès que
le nom du contrôle attendu figurait dans la sortie — or le rapport nomme tous
les contrôles, réussis compris. Il lit désormais la ligne de synthèse des
échecs. Les tests unitaires ont ensuite montré que le gabarit brut d'une
demande passait le lint : ses textes à remplacer contiennent les mots que le
lint cherche. Un trou laissé tel quel est maintenant refusé.

Le dogfooding a ensuite fait refuser trois commandes légitimes par les hooks
de ce dépôt : un heredoc qui citait la commande de réponse humaine sans la
lancer, une référence `commit:` lue à travers un accent grave fermant, et
l'exécution du lanceur prise pour une écriture d'un fichier protégé. Les
trois motifs ont été resserrés, chacun avec son test.

## J-2026-10-10-G — Porte du jalon 5, en local : la commande de CI refuse une pull request défectueuse

## J-2026-10-10-S — Un test exigé pour le code nouveau ou modifié

> type : jalon · ref : fichier:moteur/socle/controles_tests.py, fichier:tests/test_code_teste.py

Accepté par Théo (J-2026-10-10-R). Le contrôle `tests.code-teste` exige
qu'une fonction publique ajoutée ou modifiée depuis la base soit nommée par
au moins un test, ou dispensée nommément par un trailer de commit
`Dispense-test: f, g — <raison>`. Ce qui est du code, et ce qui rend une
fonction privée, vient de l'adaptateur (section `[code]`), ou à défaut de
l'adaptateur maintenu du même langage.

Première exécution sur la pull request en cours : 35 fonctions sans test qui
les nomme, dont 10 privées. Des 25 publiques, 19 ont désormais leur test
(`tests/test_cli.py`, `tests/test_code_teste.py`, `tests/test_liens.py`,
`tests/test_lectures.py`) ;
les 6 autres sont des hooks, une aide de contrôle et le harnais de
l'auto-test, que l'auto-test éprouve par leurs vrais points d'entrée sans les
nommer : le commit les dispense un par un, avec cette raison.

La règle pour le code existant qu'on découvre sans test entre dans les
instructions : le test s'écrit tout de suite s'il est dans le périmètre du
travail, sinon un sujet va au backlog.

## J-2026-10-10-T — Backlog clos archivé : B-0014

### B-0014 — Exiger un test pour du code nouveau, et pour du code existant qu'on découvre non testé

> statut : fait · origine : J-2026-10-10-J · ref : J-2026-10-10-S

Demandé par Théo. Le cadrage ne l'impose pas : il exige un test de
régression pour un correctif, et compte sur la mutation pour voir le code
qu'aucun test ne vérifie — or la mutation est hebdomadaire et absente pour

## J-2026-10-10-W — Jalon 6 : le socle sur un projet Python jetable, avec pytest et mutmut

> type : jalon · ref : fichier:moteur/socle/adaptateurs/python-pytest.toml, commit:4c94154, commit:fcc5e4e

Un projet jetable, hors du dépôt : `romains`, un convertisseur de chiffres
romains (deux fonctions publiques, 23 tests pytest), avec son dépôt
d'origine local. Le socle s'y installe avec un adaptateur maintenu nouveau,
`python-pytest` : pytest pour les tests et le rejeu des correctifs, mutmut
pour la mutation, qui exige pytest. L'adaptateur `python` reste celui des
projets sous `unittest` seul, comme ce dépôt.

Ce qui tourne sur le projet : l'installation et son audit, `socle ci`
(vérification, contrôles contre la base, auto-test), un balayage `mutmut`
(34 mutants : 25 attrapés, 6 trop longs, 3 survivants, deux messages
d'erreur que les tests ne lisent pas et une condition redondante) et le
verdict contre un plafond de 3. Défauts injectés, chacun attrapé :

- un test sans assertion : refusé au commit et en CI (`tests.creux`) ;
- un test supprimé : refusé au commit et en CI (`tests.attendus`) ;
- une fonction publique sans test : refusée en CI (`tests.code-teste`) ;
- un correctif sans test de régression : refusé en CI (`tests.regression`) ;
  avec son test, il passe, le test échouant sur le commit d'avant ;
- des tests affaiblis : 5 survivants pour un plafond de 3, verdict en échec.

La porte : le noyau inchangé. Les contrôles, la mémoire et les hooks n'ont
pas changé. Deux corrections du moteur ont été nécessaires, chacune avec un
test qui échoue sur son parent : le lecteur des résultats de mutmut, propre
à l'outil, écrit au jalon 3 sans avoir tourné ; et `tests.code-teste`, qui
prenait le moteur installé dans `.socle/` pour du code du projet, ce que
seul un projet Python pouvait montrer puisque le moteur est en Python.

Trouvé aussi, et réglé dans l'adaptateur : `mutmut results` omet par défaut
les mutants attrapés (d'où `--all true`) ; mutmut garde en cache le résultat
d'un mutant tant que le code ne change pas, même quand les tests changent, et
le premier essai de tests affaiblis rendait un verdict périmé (le dossier
`mutants/` est effacé avant chaque balayage) ; pytest ramassait la copie des
tests que mutmut laisse dans ce dossier (`--ignore=mutants`).

Le hook de l'agent a refusé un push vers la branche `main` du dépôt
d'origine local du projet jetable : il ne distingue pas un dépôt local d'un
dépôt distant. L'essai s'en est passé en clonant l'origine.

## J-2026-10-10-Y — Jalon 7 : la mémoire privée, en dépôt compagnon et chiffrée

> type : jalon · ref : fichier:moteur/socle/prive.py, fichier:tests/test_prive.py

Ce qui ne dépend pas des trois arbitrages en attente (D-0006, D-0007,
D-0008) est construit :

- la zone privée memoire/prive/ se lit avec le reste de la mémoire : le
  clone du dépôt privé, que git ignore, compte parmi les fichiers ; un
  fichier privé chiffré ici compte pour absent ;
- mode compagnon : le verrou .socle/prive.lock, `socle prive verrouiller`,
  `socle prive extraire`, `socle prive recuperer` pour la CI ; le contrôle
  `prive.verrou` refuse un fichier privé commité dans le dépôt public, un
  verrou périmé, un changement privé hors commit ;
- mode chiffré : le moteur ne connaît pas l'outil ; `prive.chiffre` refuse un
  fichier privé commité en clair, ou une zone privée qu'aucun filtre ne
  couvre ;
- `prive.acces` et l'état dérivé disent « INDISPONIBLE » quand le clone ou la
  clé manquent ; des fichiers privés commités sans mode sont refusés ;
- en CI, un constat de la zone privée ne montre ni son texte ni son chemin ;
- la zone privée suit les budgets de la zone publique ; `socle new` écrit en
  privé par défaut quand une mémoire privée existe.

La porte du jalon : sur un projet public d'essai, l'audit passe dans les deux
modes et une fuite injectée est attrapée. L'auto-test prépare deux projets
d'essai, l'un en mode compagnon, l'autre chiffré par un filtre git
réversible ; les témoins passent dans les deux modes (y compris sans la clé,
comme une CI de fork), et sont attrapés : un fichier privé commité en clair,
un verrou périmé, la mémoire privée inaccessible au démarrage, un
identifiant privé dans un fichier public. Le défaut « mémoire privée non
accessible » du cadrage, déclaré non couvert jusqu'ici, l'est désormais.

Régénérer les instructions de ce dépôt réécrit aussi son workflow de CI, qui
gagne l'étape de récupération de la mémoire privée ; ce fichier est
protégé, et la réécriture a été retirée du travail : à toi de l'accepter.

## J-2026-10-10-AC — Jalon 8 : installeur, entrées d'initialisation, adoption et mise à jour

> type : jalon · ref : fichier:moteur/socle/initialisation.py, fichier:moteur/socle/installeur.py, fichier:tests/test_initialisation.py

Sur des copies locales jetables, comme Théo l'a décidé (D-0005) :

- **L'installeur** déduit l'adaptateur du dépôt (`--adapter auto` : Rust,
  Python sous `unittest`, ou sous pytest), refuse et renvoie la question à
  l'humain quand rien ne le dit, et pose la mémoire privée choisie
  (`--private compagnon|chiffre`, avec la relecture et les demandes
  privées) en vérifiant l'accès au dépôt privé ou au filtre.
- **La mise à jour** : relancé, l'installeur remplace le moteur, applique
  les migrations de format dans l'ordre (le verrou note le format ; une
  migration manquante arrête tout), et montre le diff de la politique avec
  le gabarit, sans la toucher.
- **`socle init`** : le document de cadrage archivé tel quel, avec son
  empreinte au journal ; l'audit du dépôt en lecture seule, dont ne sortent
  que des faits mesurés, chacun avec son fichier pour preuve ; les questions
  de départ, chacune avec son défaut, plafonnées par la politique, en une
  demande au contrat (réponses `defauts`, `reponses`). Ce qui demande de
  comprendre revient à l'agent, avec des règles imprimées.

La porte, sur des copies : l'installation sur une copie de chess passe en
trois secondes, adaptateur Rust détecté, sans merge à la main ;
l'initialisation réussit depuis chacune des entrées — rien (un dépôt vide),
le cadrage de ce dépôt seul, chess seul, chess avec un cadrage — et
`check --stage ci` passe ensuite. Un fait tiré du cadrage, « supposé » avec
sa source, passe ; un fait « mesuré » sans preuve est refusé.

Trouvé en route : l'audit comptait pour « fichiers de test » tous les
fichiers source d'un projet Rust, dont les tests unitaires vivent dans les
sources ; il compte désormais les fonctions de test elles-mêmes (347 dans
20 fichiers, pour chess). La CI que le socle pose n'entre pas dans l'audit.
Le hook de l'agent refuse de modifier une politique même dans une copie
jetable : la mise à jour s'éprouve par des tests unitaires.
