## J-2026-11-21-H — T-0025 : relancé avant le commit d'une mise à jour, l'installeur lit les notes déjà vues dans la copie du moteur du dernier commit

> ref : T-0025, B-0225, L-0008, ADR-0078, ADR-0052

Un sous-agent du lot L-0008 (Opus 5.5) fait T-0025. L'installeur lisait
les notes de version déjà vues dans la copie du moteur de l'arbre :
relancé avant le commit d'une mise à jour, il y trouvait la copie neuve,
et le message de commit proposé comme l'étape qui ouvre l'agent ne
nommaient plus les notes. `notes_deja_lues` (`engine/socle/installer.py`)
les lit désormais dans la copie du dernier commit (`git ls-tree`, puis
`git show HEAD:<chemin>`), comme `versions_maintenues` lit le moteur
installé (ADR-0052).

Le choix : le repli sur l'arbre ne se fait que si le dépôt n'a pas de
commit, ou si le dernier commit n'a pas de copie du moteur à cet
endroit ; un dernier commit qui a la copie sans fichier de notes (un
moteur d'avant ADR-0078) n'en a lu aucune, et la mise à jour relancée
les redonne toutes, au lieu de se replier sur l'arbre déjà neuf.

Les tests de `tests/test_notes_de_version.py`
(`test_relancee_avant_son_commit_elle_nomme_les_memes_notes`,
`test_une_copie_commitee_sans_notes_les_recoit_toutes_meme_relancee`,
`test_notes_deja_lues_dans_le_dernier_commit_sinon_dans_l_arbre`)
échouent sur le commit parent. Aucune valeur attendue n'a changé : les
tests existants ne commitent jamais l'installation, et le repli sur
l'arbre leur garde leur résultat. Note de version 2026-11-21-a ;
l'architecture le dit.

## J-2026-11-21-I — T-0028 : une mise à jour en automatique ne pose plus d'adaptateur du langage d'une copie déjà posée

> ref : T-0028, B-0144, L-0008, ADR-0051, ADR-0052

Un sous-agent du lot L-0008 (Opus 5.5) fait T-0028. Reproduit d'abord :
un projet Kotlin dont Python est le second langage (`outils/pyproject.toml`,
un dossier de tests Python à la racine) reçoit sa copie python.toml
dans le dossier des autres adaptateurs ; un `conftest.py` neuf, et la mise à jour
en automatique posait `python-pytest.toml` à côté,
`adaptateur.recouvrement` en échec sur chaque fichier Python.

La boucle de `_installer` (`engine/socle/installer.py`) lit désormais
le langage de chaque copie de ce dossier (`_langages_des`, que
`langages_en_place` reprend) : un adaptateur détecté ou nommé d'un
langage qu'une copie couvre sous un autre nom devient cette copie, son
nom et son texte, que `_poser_autres_adaptateurs` rafraîchit ou garde
comme avant (ADR-0052).

Le choix : remplacer par la copie plutôt que d'écarter l'adaptateur.
Écarté, un `--adapter python-pytest` nommé seul aurait laissé vide la
liste des autres, et la condition qui garde le principal pour la CI
(« le premier nommé n'est pas le principal ») ne tenait plus : la CI
serait partie de `python-pytest`. Remplacé, tout se passe en aval comme
si l'on avait nommé la copie. Rien n'est dit de plus, comme pour un
adaptateur du langage du principal.

Les tests `test_une_mise_a_jour_automatique_garde_la_seule_copie_python`
et `test_nomme_l_adaptateur_d_un_langage_que_couvre_une_copie_est_la_copie`
(`tests/test_adaptateurs_multiples.py`) échouent sur le commit parent ;
`test_langages_en_place_lit_chaque_copie` nomme la fonction modifiée.
Note de version 2026-11-21-b, qui dit quoi faire d'un doublon déjà
posé ; l'architecture le dit. Le guide ne dit rien de contraire.
